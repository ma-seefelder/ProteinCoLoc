# Re-blessing the D-09 calibration golden

**Scope:** `test/gate/ci_golden.jl` and the Tier-2 golden blocks in `test/gate/p15_consts.jl`.
**Read this before you touch either.** It is written to be followed under time pressure, which is
the only condition under which it matters.

---

## 0. The thing to know first

**A red golden is the gate working.**

The fast tier (`.github/workflows/ci.yml`) asserts that the shipped 8×8 net, the summary chain, the
standardizers, the flow forward pass and the draw order all produce the same rank table they
produced when the golden was blessed. When it goes red, something in that chain changed. The job of
whoever sees the red is to find out **what**, not to make the red go away.

---

## 1. WHEN re-blessing is legitimate

Exactly three reasons. Each must be named, in the reason string and in the commit message.

| # | Reason | What the commit message must also say |
|---|---|---|
| 1 | **A Julia patch-version bump.** `seed_gate_global!` ends in `Random.seed!` on Julia's default task-local RNG, whose stream semantics are **not** a cross-version contract. A bit-exact golden is therefore a Julia-patch assertion as much as a code assertion. | The OLD and the NEW version, explicitly (e.g. "1.12.6 → 1.12.7"), and the matching bump of `version:` in `.github/workflows/ci.yml`. |
| 2 | **A deliberate, reviewed change to the inference path** — the net, the summary chain, the standardizers or the flow. | Which change, and where it was reviewed. |
| 3 | **A re-shipped net** (a new `grid_8` artifact hash). | The old and the new `Artifacts.toml` `git-tree-sha1`. |

Nothing else.

## 2. WHEN it is NOT

**A red CI run nobody has explained.**

Say it plainly: re-blessing to make a red run green is the *"tune until it passes"* move. This
project's `STATE.md` records that it has already concluded "the bar was wrong, not the model" **four
times**, and that the count is now high enough that "we pre-registered it" no longer settles an
argument on its own. A golden that can be regenerated by whoever is annoyed by it is not a control;
it is a rubber stamp with extra steps.

If you cannot state which of the three reasons in §1 applies, **you do not have a re-bless — you
have an unexplained regression.** Find it.

## 3. THE COMMAND

```bash
julia --project=. --threads=auto test/gate/ci_golden.jl --rebless --reason "..."
```

The reason may also be supplied as the `P15_REBLESS_REASON` environment variable (for scripts that
would otherwise fight shell quoting). It is not optional either way.

**Without a reason the script exits 3, prints the list in §1, and writes nothing.** That refusal is
asserted by `test/gate/test_p15_golden.jl` testset 3, which byte-compares the whole pre-registration
file before and after.

**With a reason it:**

1. measures — one fixture-scale SBC run at `P15_GOLDEN_M = 8`;
2. prints OLD and NEW side by side, in a form that pastes into a commit message;
3. **APPENDS** a new sentinel-keyed Tier-2 block to `test/gate/p15_consts.jl`, taking the next free
   sentinel in the `:P15_GOLDEN_RANK_DIGEST`, `_V2`, `_V3`, … sequence, carrying the new values, the
   reason string, the date and the Julia version.

It **never** edits or deletes the previous block. `p15_golden_check` reads the **highest-numbered**
block present, so an append supersedes without any rewrite. The git history of `p15_consts.jl` is
the audit trail; that is the whole design.

## 4. WHAT THE COMMIT MUST CONTAIN

- **The appended block, and nothing else, in `p15_consts.jl`.** No edits above it. Verify:
  ```bash
  git diff -U0 HEAD -- test/gate/p15_consts.jl | grep -E '^-[[:space:]]*const '   # must print nothing
  ```
- **The reason** in the commit message body — the same string passed to `--reason`.
- **The printed OLD and NEW table** from step 2, pasted into the commit message. A reader must be
  able to see what moved without re-running anything.
- **The Julia version** the new values were measured on.

## 5. THE GUARD

`test/gate/test_p15_golden.jl` fails the suite if any `const` declaration line in `p15_consts.jl`
was **modified** rather than appended (CONVENTIONS C-03: `git diff -U0 <base> -- <file>`, narrowed
to changed `const ` declaration lines; a surviving `-` line is by construction a pre-registration
breach). The guard is shown to fire on a synthetic diff in testset 6, so it is a test and not an
assurance. It runs locally **and** in the fast tier, and it skips honestly — never silently passes —
when git or the base ref is unavailable, as on a shallow CI checkout.

Testset 4 additionally proves, on a temp copy, that the append leaves every line of the previous
block byte-identical and that the new block carries a distinct sentinel.

## 6. THE HONESTY NOTE

Quoted from `P15_GOLDEN_HONESTY` in `test/gate/p15_consts.jl`:

> At M = `P15_GOLDEN_M` = 8 the ECE null mean is ~0.336/sqrt(8) ~= 0.12 — an order of magnitude
> above any miscalibration worth detecting. The fast gate therefore detects **CHANGE** (a bit-level
> regression in the net, the harness or the statistic), **NOT** miscalibration. Miscalibration is
> detected by the SLOW tier at reported scale. Any claim that the per-push CI proves calibration
> oversells SC3.

So: a green golden is **not** evidence of calibration, and re-blessing it does **not** re-establish
calibration. Those are the slow tier's job. What a re-bless does is move the change-detection
baseline — which is exactly why it has to cost a reason and a commit.
