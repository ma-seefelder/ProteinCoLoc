# Phase 15 — Validation Strategy

> Per-phase validation contract for feedback sampling during execution.

**Phase-specific note.** This phase's *deliverable* is partly a test gate, so "validation" here has
two layers that must not be conflated:

- **Layer A — validating the phase's own code** (generators, consts, runner, CI workflow). Ordinary
  unit tests, fast, run continuously during execution. This document governs Layer A.
- **Layer B — the calibration gate the phase SHIPS** (the golden-value fast tier, D-09). That is a
  deliverable under test by Layer A, not a sampling instrument for it. A green Layer B tells you the
  gate runs; it does not tell you the gate is correct.

---

## Test Infrastructure

| Property | Value |
|----------|-------|
| **Framework** | Julia stdlib `Test` (`@testset`), via `test/runtests.jl` |
| **Config file** | `Project.toml` (root) + committed `Manifest.toml` — pinned, not resolved |
| **Quick run command** | `julia --project=. --threads=auto test/gate/test_p15_*.jl` |
| **Full suite command** | `julia --project=. --threads=auto -e 'using Pkg; Pkg.test()'` |
| **Estimated runtime** | quick: target < 60 s · full: **to be measured in Wave 0** (includes the co-resolution gate and existing gate tests) |

**`--threads=auto` is mandatory, not an optimisation.** Research measured single-threaded execution
at ~13× slower. Any command in this phase that omits it produces a misleading runtime and may exceed
the CI job budget.

---

## Sampling Rate

- **After every task commit:** Run the quick command (Phase-15 unit tests only).
- **After every plan wave:** Run the full suite.
- **Before `/bm:verify-work`:** Full suite green, and the D-09 golden gate green against its
  committed reference.
- **Max feedback latency:** 60 s for the quick command.

**Explicitly NOT a sampling instrument:** the sweep itself (~8.5 h). It runs once, under its own
budget ceiling, and is verified by artifact inspection — never re-run to check a code change.

## Manual-Only Verifications

| Behavior | Decision Ref | Why Manual | Test Instructions |
|----------|--------------|------------|-------------------|
| The GitHub Actions workflows actually run on a hosted runner | D-08 | Cannot be verified locally — the runner OS, the `Pkg.instantiate()` path, and the GLMakie/OpenGL headless requirement only exercise on GitHub's infrastructure | Push a branch, confirm both the fast tier (push trigger) and the slow tier (`workflow_dispatch`) start, and that the co-resolution gate passes under instantiate-from-manifest |
| The golden gate FAILS on real calibration drift | D-09 | A gate that never fires is indistinguishable from a passing one; this requires deliberately perturbing inference and confirming a red run | Introduce a temporary, uncommitted perturbation to the inference path, confirm the fast tier goes red, revert. **Record the observed failure** — a regression gate never seen to fail is not evidence |
| The re-bless procedure is followed | D-09 | A process control, not a code property | Confirm the golden cannot be regenerated by any committed script without an explicit, reasoned commit |

**The second row is the one that matters.** SC3 claims a test "fails CI on calibration drift". That
claim is only supported by having *observed* it fail.
